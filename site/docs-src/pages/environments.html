Environments and variables

An environment is a named set of variables, such as local, staging or production. Write {{baseUrl}} in a request once, and switch where it points with one shortcut.

Using variables

Write {{name}} in the URL, a query parameter, a header name or value, a form field or a JSON, XML or text body. Spaces inside the braces are allowed: {{ name }} is the same variable. When the request is sent, each marker is replaced with its value.

```postino GET {{baseUrl}}/accounts/{{accountId}}/orders Authorization: Bearer {{token}} ::: query since = {{since}} ```
  • In the URL bar, every variable is drawn as a chip. A variable with no value shows as a red chip.
  • A variable with no value is sent literally, as {{name}}, and the response shows an Unknown variable warning. It never stops the request.
  • Variables are replaced in one pass: if the value of outer is {{inner}}, the request contains the text {{inner}}, not the value of inner.
  • A {{ with no closing }} is left alone, without a warning.
  • Inside the braces you can also call a template function, such as {{ uuid() }}.
  • Scripts are not interpolated: inside ::: pre and ::: post, read variables with vars.get() and env.get().

Environment files

Environments live in the environments/ folder at the root of the workspace. Each one is up to two files:

environments/<name>.env
The shared values: hosts, user names, feature flags. Commit it.
environments/<name>.local.env
Secrets and personal overrides: passwords, tokens, API keys. Its values win over <name>.env. Keep it out of git.
```env title="environments/staging.env" # Staging, shared by the whole team baseUrl=https://staging.api.example.com username=qa-bot timeout=5000 ``` ```env title="environments/staging.local.env" password=correct-horse-battery-staple apiKey=sk_test_51H... ```

The format is one KEY=value per line. Lines starting with # are comments. The value is everything after the first =, kept exactly as written: no quotes, no escaping and no trimming. The full rules are in the file format reference.

Keep secrets out of git

Postino does not edit your .gitignore. Add this line to it once per repository:

```text title=".gitignore" *.local.env ```

Switching environments

  • Click the environment pill in the title bar and choose one, or No environment.
  • Press Ctrl 1 to Ctrl 9 (⌘ on macOS) for the first nine environments in alphabetical order, and Ctrl 0 for no environment.
  • Use the Environments group of the command palette.
  • In the Environments panel, or in an environment's editor, choose Use this environment.

The active environment of each workspace is remembered and selected again when you reopen it. It is stored in Postino's configuration, not in the workspace.

Resolution order

When Postino replaces {{name}}, it looks in these layers and uses the first one that has the variable:

  1. Pre-request variables. Set with vars.set() by the pre-request script of this run. They exist only for this one send.
  2. Session variables. Set with env.set() by any script since Postino started. They are shared by every request and disappear when you quit.
  3. .local.env of the active environment.
  4. .env of the active environment.

If no layer has it, the variable is unknown. A disabled entry is skipped as if it were not there. If a file defines the same name twice, the first definition is the one used.

The environment editor

Click an environment in the Environments panel to open it in a tab.

  • Files. The header shows the two files of the environment, marked versioned (.env) and gitignored (.local.env), or not created when a file does not exist yet.
  • Scope. All shows the merged view: every variable once, with the .local.env value where it overrides .env, plus the session variables. Or pick one file to see only its rows.
  • Stored in. Each variable shows the file it lives in. The Move to the other file button moves it between .env and .local.env in one click. A .local.env row that hides a .env value says Overrides the value in ….
  • Secrets. Values stored in .local.env are masked. Show secrets reveals them.
  • Session values. Variables set by scripts during this session are listed as session, with the note Set by a script · cleared on quit.
  • Filter narrows the list by name. Add variable adds a row to .env, and the remove button deletes a row.
  • Press Ctrl S to save. Closing a tab with unsaved changes asks first.

Saving rewrites only the lines you changed: comments, blank lines and the order of everything else stay as they were. The .local.env file is created when you first store a variable in it.

Saving is refused, with a message, when a row has a value but no name, a name contains = or a line break or starts with #, a value contains a line break, or the same name appears twice in one file.

Environment actions

The More actions menu of the editor has:

  • Rename, which renames both files.
  • Reveal in file manager, which opens the environments/ folder.
  • Delete, which removes both .env and .local.env after asking. It cannot be undone.

Creating an environment

  1. Open the Environments panel from the activity rail.
  2. Click New environment, type a name and press Enter.
  3. Postino creates environments/<name>.env, creating the folder if needed, and you can start adding variables.

You can also create the files by hand in any editor. An environment exists as soon as its .env file does.

Defining a variable from a request

When a request uses a variable that has no value, you do not need to leave the request to define it:

  1. Click the red chip in the URL bar, or Define on the Unknown variable warning of the response.
  2. The Define variable dialog asks for the value and the environment. It preselects the active environment, or the first one. Choose New environment… to create one on the spot.
  3. Store in .local.env (not versioned) decides where the value goes. It is switched on for you when the name looks like a secret: when it contains token, secret, password or key, ignoring case.
  4. Press Save. The value is written to the file right away.

Session variables

A post-response script can store a value for later requests with env.set(). The typical case is a login request that keeps the token:

```js env.set("token", res.json().access_token); ```

Session variables:

  • take priority over both environment files;
  • are shared by every request until you quit Postino;
  • are never written to an .env file;
  • show in the environment editor as session;
  • can be removed with env.unset("token").

To keep a value across restarts, copy it into the environment in the editor.

Request variables

A pre-request script can set a variable for the current send only, with vars.set(). It has the highest priority and is gone when the run ends:

```postino POST {{baseUrl}}/payments Idempotency-Key: {{requestId}} ::: pre vars.set("requestId", util.uuid()); ```

Postino recognizes vars.set("name", …) calls with a literal name in the pre-request script, so those variables are not flagged as unknown in the URL bar before you send.
