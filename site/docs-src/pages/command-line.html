title: Command line description: Start Postino from a terminal with a workspace folder or a request file, run requests and send one-off requests without the window, the exit codes, and the environment variables it reads at startup. ---

Command line

The postino binary opens the app on a folder or a request, and it also works without the window: it runs .postino requests and load tests, and sends one-off requests like curl, printing the results in the terminal. That second mode needs no display, so it works on servers and in CI pipelines.

Usage

```shell $ postino [OPTIONS] [PATH] # opens the window $ postino [ARGS] # runs in the terminal ```

When the first argument is one of the commands below, Postino runs in the terminal and exits: no window, no settings read, nothing written to the log. Anything else opens the app. A folder named like a command opens with a path that does not look like one, such as postino ./run.

Opening the app

The binary is postino on Linux (installed to /usr/bin by the packages), postino.exe in %LOCALAPPDATA%\Programs\Postino on Windows, and /Applications/Postino.app/Contents/MacOS/postino on macOS.

PATH isPostino opens
MissingThe last workspace you used, if the folder still exists. Otherwise the welcome tab.
A folderThat folder as the workspace.
A .postino fileThe remembered workspace if it contains the file, otherwise the file's folder, and then the file in a tab.
A path that does not existAn error saying the workspace could not be opened, with the welcome tab open behind it so there is something to click.
```shell # Open the requests that live in a repository $ postino ~/code/shop/api-requests # Open one request $ postino ~/code/shop/api-requests/orders/create.postino ```

Starting Postino with a path never opens the welcome tab: you asked for something specific. The only exception is the path that cannot be opened, in the table above. Opening a .postino file from your file manager counts as a path.

Only the first argument is read when opening the app, so an option and a path are never combined. Postino is not single instance: running it again, or double clicking a .postino file while it runs, starts a second window process.

Options

These print to the terminal and exit with code 0, without opening the window, reading the settings or writing to the log.

OptionPrints
-h, --helpA summary of the usage, the options and the environment variables below, with a link to this page.
-V, --versionThe name and version, such as Postino 0.4.0. A development build, made between two releases, has a -dev version and adds the short commit it was built from, such as Postino 0.5.0-dev (9bb54cc); quote it when you report a bug. The first line of --help is the same.
```shell $ postino --version Postino 0.2.0 ```

The output is always in English, whatever the Language setting says. On Windows, see Windows for how to wait for the commands to finish.

Commands

CommandDoes
run [PATHS]Runs requests, folders or the whole workspace, with their scripts and tests.
checkChecks that every request, environment and the project file of the workspace can be read.
load [PATHS]Runs a load test, with a live dashboard on a terminal.
get, post, put, patch, delete, head, options <URL>Sends one request with that method, like curl.
http <METHOD> <URL>Sends one request with any method, custom ones included.

postino <COMMAND> --help lists the options of a command. The output is always in English. For a step by step setup in a pipeline, see Running in CI.

Workspace and variables

Every command takes these options:

OptionEffect
--workspace <DIR>The workspace folder. Without it, Postino looks for the nearest folder holding a .postino folder, starting at the first path given to run, or at the current directory. When there is none, run and check use that starting folder itself, and one-off requests use no workspace.
-e, --env <NAME>The environment to use, a file name under environments/ without .env. Its .local.env is merged in, as in the app. An unknown name exits with code 4 and lists the ones that exist.
--env-file <FILE>A .env file whose variables win over the environment's.
--var <KEY=VALUE>One variable, repeatable. It wins over the environment and the --env-file.
--no-colorNever prints colors. Colors are only printed to a terminal, and the NO_COLOR environment variable turns them off too.

The commands that send requests also take the options of the Network settings. The settings of the app are not read: without these options, the defaults apply.

OptionEffectDefault
-k, --insecureAccepts any TLS certificate, with no warning.An invalid certificate is accepted with a warning, printed under the request.
--timeout <TIME>The time limit of a request: 500ms, 30s, 2m, or a number of seconds.30s
--max-size <SIZE>The largest response body read: 512kB, 50MB, 1GB, or a number of bytes.20MB. No limit when -o saves the body to a file.
--proxy <URL>The proxy, such as http://proxy:3128 or socks5://localhost:1080.The HTTPS_PROXY family of environment variables.

run

```shell $ postino run auth/login.postino # one request $ postino run auth/ crud/ # folders, recursively $ postino run # the whole workspace ```

Requests go through the same steps as Send in the app: the OAuth 2.0 token, the pre script, the variables, the request, the post script and its test() calls. They run one after the other, in the order the paths are given and, inside a folder, in the order of the sidebar. A request named twice runs once. A value a script stores with env.set() is seen by the requests that follow, as in the app.

OptionEffect
--bailStops at the first request that fails.
--filter <PATTERN>Runs only the requests whose path matches, repeatable. * matches any text, slashes included, and ? one character. The .postino extension is optional: 'auth/*', '*login*'.
--show-bodyPrints each response body under its request.
--output <FORMAT>human (the default), json or junit.
-o, --output-file <FILE>Writes the json or junit output to a file, and the readable lines to the terminal.
```text title="postino run --env local auth/ scripting/" ✓ auth/login POST 200 84 ms 2/2 tests ✓ auth/login-wrong POST 401 12 ms 1/1 tests ✗ scripting/test-failure-does-not-stop GET 200 3 ms 2/3 tests ✗ this one fails on purpose: expected 200 to be 500 3 requests, 1 failed · 5/6 tests passed · 99 ms ```

A request fails when a test fails, when its pre or post script throws, when its OAuth token cannot be obtained, or when nothing comes back. The reason is printed under it, followed by the console.log lines of its scripts. A variable that did not resolve and a certificate that was not verified are printed as warnings (!) and do not fail the request.

With --output json, each request is one line of JSON, and a last line has the totals:

```json {"type":"request","request":"health.postino","method":"GET","url":"http://127.0.0.1:8080/health","status":200,"time_ms":3,"size":42,"passed":true,"tests":[{"name":"server is up","passed":true,"message":null}],"error":null,"warnings":[]} {"type":"summary","requests":1,"failed":0,"tests":1,"passed_tests":1,"time_ms":3,"exit_code":0} ```

The url leaves out the query string, which may hold secrets. status and size are null when nothing came back. With --output junit, each request is a test suite and each test() a test case. A request that did not run to the end adds a test case named request with an error, and so does a request without tests, passed.

check

```shell $ postino check ✓ 164 requests and 2 environments, all valid ```

Reads every .postino file, every environment (with its .local.env) and .postino/project.toml, and prints the ones that cannot be read with the reason. Nothing is sent. It exits with code 4 when there is a problem. --output json prints one line per problem and a last line with the totals.

load

```shell $ postino load crud/list-users.postino --vus 50 --duration 2m $ postino load auth/login.postino crud/ --vus 20 --ramp-up 30s --think 200ms ```

Runs a load test with the same engine as the app: every virtual user loops over the requests in order, through their scripts, and what one script stores with env.set() reaches the next request of the same virtual user. Without a path, the whole workspace is the target. The OAuth 2.0 tokens are obtained once before the run starts; a token that cannot be obtained stops the command before any request is sent.

OptionEffectDefault
--vus <N>Virtual users at full ramp-up, from 1 to 500.50
--duration <TIME>How long the run lasts, from its start.60s
--ramp-up <TIME>How long it takes to start every virtual user, at even intervals.10s
--think <TIME>The pause of a virtual user after each pass over the requests.0s
--no-keep-aliveOpens a new connection for every request. See Connections.Keep-alive
--stop-on-error <RATE>Ends the run early when the error rate goes above the rate, such as 5%, once at least 50 requests have completed. The run then exits with code 1.Off
--fail-if <CONDITION>A condition that fails the run when it holds at the end, repeatable. See below.
--no-tuiPrints a progress line every 5 seconds instead of the dashboard.The dashboard on a terminal
--report <FILE>Writes a report when the run ends, in the format of the extension: .pdf, .md, .json or .csv. They are the same files as Export in the app.
--no-saveDoes not save the run to the run history.Saved
--compare <RUN>Compares the run with a saved one: last, the latest run with the same target, or a run number.

A condition is a metric, >, >=, < or <=, and a limit, checked over the whole run:

MetricLimitExample
p50, p95, p99, avg, maxA latency in ms (the default unit) or s.'p95>500ms'
errorsThe error rate, a percentage.'errors>1%'
rpsThe average requests per second.'rps<100'

Quote a condition, since > and < redirect in a shell. An upper bound of p50, p95, p99 or errors and a lower bound of rps are saved with the run as its thresholds, so the app checks the run against them too.

On a terminal, a dashboard shows the progress, the requests, the requests per second and the error rate with their recent history, the latency percentiles, a chart of the p50 and p95 of each second, the statuses and a table per request. It redraws four times a second.

KeyDoes
q, Esc, Ctrl+CStops the run. It ends once the requests in flight complete; a second Ctrl+C quits at once.
pPauses or resumes. While paused no request starts, and the end of the run moves later by as long as the pause lasts.
sSaves a report of the run so far to the --report file, or to run-NNNN.md in the current directory.

When standard output is not a terminal, as in CI, or with --no-tui, a progress line is printed to standard error every 5 seconds, and Ctrl+C stops the run cleanly. Either way, the run ends with a summary on standard output: the totals, the latency, the statuses, the table per request, the comparison and each condition.

```text title="postino load health.postino --env local --vus 10 --duration 6s --ramp-up 2s --fail-if 'p95>500ms'" postino load · health · 10 VUs · 6s · ramp-up 2s · think 0s · keep-alive Finished after 00:06 Saved as run 1 in .postino/runs Requests 27891 RPS 4647.1 Errors 0.0 % Latency p50 <1 ms p95 1 ms p99 2 ms avg <1 ms max 3 ms Status 200 × 27891 Request Count p50 p95 p99 Errors GET health 27891 <1 ms 1 ms 2 ms 0.0 % Fail if ✓ p95 > 500 ms was 1 ms ```

A load test exits with code 1 when a condition holds, when --stop-on-error ended it, or when no request completed, and with code 3 when no request got a response at all. A 4xx or 5xx response counts in the error rate but does not change the exit code by itself: use --fail-if 'errors>0%' for that.

One-off requests

```shell $ postino get https://api.example.com/users $ postino post https://api.example.com/login --json '{"user":"ada"}' $ postino http PURGE https://cdn.example.com/assets/app.js $ postino get https://example.com/big.iso -o big.iso ```

The response body goes to standard output untouched, so it can be piped to jq or saved with >. A summary line with the status, the time and the size goes to standard error, with any warning. Inside a workspace, the URL, headers and body take {{variables}} from --env, --env-file and --var, and template functions work too.

OptionEffect
-H, --header <'Name: Value'>A header, repeatable.
-q, --query <KEY=VALUE>A query parameter, repeatable.
-d, --data <TEXT>A raw text body. @file sends the text of a file, and @- reads it from standard input.
--json <TEXT>A JSON body, sent with Content-Type: application/json.
-F, --form <FIELD=VALUE>A multipart field, repeatable. field=@photo.png sends a file, relative to the current directory, and @@ sends a value starting with @.
-u, --user <USER:PASSWORD>Basic authorization.
--bearer <TOKEN>Bearer authorization.
-i, --includePrints the status and the response headers before the body, on standard output.
-v, --verbosePrints what was sent to standard error: the method, the URL without its query string, and the headers, with the values of sensitive ones such as Authorization masked.
-o, --output <FILE>Saves the body to a file as it arrives, like wget, with a progress bar on a terminal. There is no size limit unless --max-size sets one. When nothing comes back, the file is removed.
--save <PATH>Saves the request as a .postino file before sending it, with its {{variables}} as written. Missing folders are created. An existing file is never replaced: the command exits with code 4.

Only one body option and one authorization option can be given. Any HTTP status, 404 and 500 included, exits with code 0: the request was sent and answered. Use run with a test() to fail on a status.

OAuth 2.0

A request whose authorization is an OAuth 2.0 profile gets its token as in the app. The client credentials and password grants need nothing else. The authorization code grant opens the system browser on the sign-in page and prints its address, in case the browser does not open; Postino waits for the redirect for up to 5 minutes. Tokens are kept in memory only, so every run gets new ones. Without a display, such as an SSH session or a CI runner on Linux, the browser cannot open: the request fails with a message that suggests a profile with the client credentials or password grant.

Exit codes

CodeMeaning
0Everything passed.
1A test() failed, a script threw, or an OAuth token could not be obtained. For load: a --fail-if condition held, --stop-on-error ended the run, or no request completed.
2The command line is wrong: an unknown option, a missing argument, a bad value.
3A network or TLS failure: nothing came back, the request timed out, or the body was larger than the limit.
4A file problem: a .postino or .env file that cannot be read, an unknown environment, a path that does not exist or is outside the workspace.

When a run has several kinds of failure, the code is the highest in this order: 4, then 3, then 1.

Environment variables

VariableEffect
POSTINO_LOGThe log level for this run: off, error, warn, info, debug or trace. Overrides the setting.
POSTINO_ENVThe name of an environment (a file name under environments/, without .env) to activate at startup.
POSTINO_AUTOSENDThe workspace-relative path of a request, such as auth/login.postino, to open and send right away.
POSTINO_IMPORTOne or more files, separated like PATH, to open in the import wizard at startup, as if dropped on the window.
TELAIO_GIT_WSL_SESSIONWindows, for a workspace inside WSL: 0 starts wsl.exe for every git command instead of keeping one running.
HTTPS_PROXY, HTTP_PROXY, ALL_PROXY, NO_PROXYA proxy for the requests Postino sends, read at startup. Lowercase names work too.

Each one does nothing when it is not set. POSTINO_ENV and POSTINO_AUTOSEND only apply to the window; the commands take --env instead.

```shell # Start with debug logging $ POSTINO_LOG=debug postino # Open a workspace on its local environment and log in straight away $ POSTINO_ENV=local POSTINO_AUTOSEND=auth/login.postino postino ~/code/shop/api-requests ```

On Windows, in PowerShell:

```shell > $env:POSTINO_LOG = "debug"; & "$env:LOCALAPPDATA\Programs\Postino\postino.exe" ```
