Importing OpenAPI

An OpenAPI or Swagger spec becomes a collection of ready to send requests: one .postino file per operation, an environment per server, auth variables kept out of git, example bodies and a status code test. A three step wizard shows everything before anything is written, and the import never overwrites a file.

Supported specs

  • OpenAPI 3.1 and 3.0, and Swagger 2.0, which is read into the same model.
  • YAML or JSON, detected from the text itself, not from the file extension.
  • $ref references inside the spec, and to other files or URLs: schemas/pet.yaml or ../common.yaml#/components/schemas/Error are read relative to the spec. A reference that cannot be read becomes a warning, and the rest of the spec still imports.

Opening the wizard

  • The Import menu in the sidebar header: OpenAPI / Swagger….
  • Import OpenAPI… in the welcome tab.
  • The command palette: Import OpenAPI spec…, or Import OpenAPI from URL…, which opens on the URL source.
  • The shortcut Ctrl Shift O (⌘ Shift O on macOS).

Step 1: Source

Three sources, chosen with the buttons at the top:

  • File: drop a spec file on the dashed area, or click it to pick one. External references are read from the disk, relative to the file.
  • URL: type the address of the spec and click Download, or press Enter to download it and go on. The download uses the same TLS settings as requests, and external references are fetched relative to the URL. Relative server URLs such as /v2 are resolved against it too.
  • Paste text: paste the spec. Pasted text has no location, so external references cannot be read.

A spec that was read shows under Found, with its title, version, format and number of operations, and the number of warnings when there are any. A text that is not a spec shows the reason in red and the wizard stays on this step.

Step 2: Options

  • Collection name: the name of the new folder, the spec's title by default.
  • Folders: Path segments puts /customers/{id} in the folder customers/{id}; Tags puts each operation in the folder of its first tag, and untagged operations at the top of the collection.

What to generate, every option on by default:

OptionWhat it writes
Environment from serversOne environment per server origin, with baseUrl set to it (https://api.acme.dev). The server path (/v2) stays in the request URLs. With one origin the environment is named after the collection; with several, each name adds the server description, or its host when there is none. Without an absolute server URL, baseUrl is http://localhost, with a warning. Turned off, the requests use the first server URL as written.
Auth variables from securitySchemesThe auth of each request, and one empty variable per scheme in environments/<name>.local.env, a file kept out of git.
Example bodiesThe body from the spec's example, or one built from the schema. Turned off, the body keeps its type and is empty.
Status code testsA ::: post script with one test() asserting the first 2xx response the spec documents.
Request documentationThe ::: docs section: summary, description and the list of parameters.

Step 3: Preview

The tree of folders and requests that will be written, every request checked. A folder's checkbox checks or unchecks everything under it, a row opens a folder or toggles a request, and Select all and None act on the whole tree. The line under the tree tells which environments and auth variables are created. Import writes the checked requests; folders left without one are not created.

The last screen tells how many requests were imported and lists the warnings. The new collection opens in the sidebar and its environments appear in the environment picker.

Importing without a workspace

With no workspace open, Import closes the wizard and opens the New workspace dialog with the collection name as the folder name. Create makes an empty folder, opens it and imports into it. Cancelling the dialog writes nothing.

How a spec maps to requests

OpenAPIPostino
OperationA .postino file, named after its summary, else its operationId, else METHOD /path
Path parameter {id}The variable {{id}} in the URL
Query parameterThe ::: query section, with the example or default value. Optional ones are disabled (#)
Header parameterA header, disabled when optional. Accept, Content-Type and Authorization are skipped, as OpenAPI says
Cookie parameterA Cookie header
JSON body (application/json, *+json)::: body json, with a Content-Type header when the type is not application/json
Form body (URL encoded or multipart)::: body form; multipart is sent URL encoded, with a warning
XML and text bodies::: body xml or text, with their Content-Type
HTTP basicBasic auth with {{<scheme>Username}} and {{<scheme>Password}}
HTTP bearer, OAuth 2 and OpenID ConnectBearer auth with {{<scheme>}}. OAuth 2 and OpenID Connect get a warning: the token has to be obtained separately
API key (header, query or cookie)API key auth, or a Cookie header, with {{<scheme>}}
security: [] on an operationNo auth

Variable names come from the scheme names, with anything but letters, digits and _ replaced by _: the scheme bearerAuth becomes {{bearerAuth}}. An operation that needs several schemes at once gets the first as its auth and the API keys of the others as headers or query entries.

A body generated from a schema takes the first value that exists among example, examples, default, const and enum, then falls back to the type: "string" (or a sample value for formats such as date-time, email or uuid), 0 or the minimum, true, and one item for arrays. allOf merges its parts, oneOf and anyOf take the first, and read only properties are left out. Recursive schemas stop instead of repeating.

A GET or HEAD operation whose body would be empty gets no body: some specs declare one by mistake.

Names are made safe for every operating system as in the Postman import, and two requests with the same name in one folder get a (2) suffix.

Example

This operation:

```yaml paths: /customers: post: summary: Create customer requestBody: content: application/json: example: {name: Ada} responses: '201': {description: Created} ```

with a server https://api.acme.dev/v2 and a global bearer scheme named bearerAuth becomes customers/Create customer.postino:

```postino POST {{baseUrl}}/v2/customers ::: auth bearer token = {{bearerAuth}} ::: body json { "name": "Ada" } ::: post test("status is 201", () => { expect(res.status).toBe(201); }); ::: docs # Create customer ```

After importing

  • Fill the auth variables in the environment, in the Environments panel.
  • Define the path variables ({{id}}) in the environment, or replace them in the URL.
  • Read the warnings: they name every scheme or body that needs attention.
