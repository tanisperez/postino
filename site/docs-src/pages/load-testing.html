Load testing

Point a load test at one request or a whole folder, choose how many virtual users to run and for how long, and watch throughput and latency live. Add thresholds to get a pass or fail verdict. Every run is saved with every request it made, so you can inspect it later, compare it with an earlier run and export it.

Only test what you own

A load test sends a lot of traffic. Run it against your own servers, or with the permission of whoever runs them. Many APIs rate limit or block clients that send too much.

Starting a load test

There are three ways to open a load test tab:

  • Right click a request or a folder in the sidebar and choose Load test…. The target is picked for you.
  • Open the Load tests panel from the activity rail and click New load test.
  • Run New load test from the command palette.

Then configure the run and press Start run.

Configuration

A value outside its range is brought back into it when the run starts. Load tests use the active environment.

Thresholds

Under Thresholds (“fails the run if missed”) you can set goals that decide whether a run passes. Press Add threshold and pick a metric; the menu lists the metrics that have no row yet, so each metric has at most one threshold. Remove a row with its button.

MetricRuleUnitValue of a new row
p50passes when the median latency is below the limitms100
p95passes when the p95 latency is below the limitms250
p99passes when the p99 latency is below the limitms500
Errorspasses when the error rate is below the limit%1
Requests/spasses when the throughput is at least the limitrequests per second100

A limit is a number of zero or more, with a comma or a period as the decimal separator; the error rate limit cannot be above 100. A row whose text is not a valid limit is ignored when the run starts. A run passes when every threshold is met, over the whole run, and is not passed when any one is missed. Thresholds never stop a run: that is what Stop on errors is for. They are saved with the run, so an old run is checked against the goals it was started with.

How a run works

  • Each virtual user is a separate thread that loops over the target: one request, or every request of the folder in order, then the think time, then again, until the duration is over or you press Stop run.
  • Every iteration runs the full pipeline: pre-request script, variables, HTTP, post-response script.
  • Each virtual user has its own copy of the session variables. A collection that starts with a login request whose post-response script calls env.set("token", …) works as expected: each user logs in and uses its own token for the next requests.
  • Stopping takes effect in well under a second, even during a long think time.
  • With Reuse connections on, each virtual user has its own connections, so 50 users against one server keep about 50 connections open.
  • The run happens on your machine. Your own CPU and network are part of the measurement, so for serious numbers use a machine close to the server.

Connections

With Reuse connections on, the default, a virtual user opens a connection with its first request and sends the next ones over it, as browsers and API clients do. Over HTTPS the TLS handshake happens once per user, not once per request, so the run measures your API rather than the cost of connecting.

Turn it off to measure clients that always connect from scratch: every request opens a new connection, with its TCP connect and TLS handshake, and closes it afterwards. Expect fewer requests per second and higher latencies, mostly over HTTPS, and a server that may run out of ports or sockets sooner.

A request to a server whose certificate is not trusted (with Invalid certificates set to Send with warning) is verified once per virtual user, and its later requests are sent without verification straight away.

Reading the results

The results update live while the run is in progress and keep their layout once it ends. Charts, tables and the tabs below work on the whole run, or on a window of it, see Selecting a window.

Header

The header shows the run number (Run #3), a badge with its state, and a line with how the run connected (Keep-alive or New connections) and when it started, as a day and a time (for example “Today 14:32”). The states are Running, Finished (the full duration elapsed), Stopped (by hand or by Stop on errors) and Failed (the run could not start). While the run is in progress the header shows a progress bar; once it ends it shows the Compare with and Export menus.

Verdict

When the run had thresholds and has ended, a strip under the header says Thresholds passed or Not passed followed by how many were missed (“1 of 3”). Next to it there is one chip per threshold with its rule (for example p99 < 50 ms or Requests/s ≥ 1,800), the value the whole run reached, and a check or a cross.

Tabs

The results have three tabs: Summary, Requests and Errors. Requests and Errors show a count: the requests of the run or window, and the requests that failed. A run saved before Postino kept every request has no detail for the last two tabs and says so, see Run history.

Summary

Requests/s, p50, p95, p99, Errors, Total
Six figures. Requests/s is the throughput over the run. p50, p95 and p99 are latency percentiles: p95 is 120 ms means that 95% of requests took 120 ms or less (nearest rank, so every value shown is a latency that actually happened). Errors is the share of requests that failed: a request counts as an error when it timed out, could not be sent, its pre-request script threw, or its status was 400 or higher. Failed tests and post-response script errors are not counted. Total is the number of requests completed. When you compare with another run, each figure also shows its change, colored as better or worse. When a threshold covers a figure, a line under it says goal followed by the rule, green when met and red when missed.
Performance over time
A chart with one point per second and two vertical axes. The left axis is for the virtual users (an area) and Requests/s; the right axis is for the latencies p50, p90 and p99. When you compare with another run, a dashed line shows the p99 of that run. A red horizontal line marks each latency threshold (“p99 goal 50 ms”). The legend above the chart turns each series on and off. Hover the chart to see a crosshair and the values of every visible series for that second.
Latency distribution
A histogram of the latencies of the requests, in 25 intervals. The width of an interval adapts to the run or window: the smallest round width with which the bars reach past the p99, shown in the caption (“requests per 10 ms interval”). The last bar adds up everything above it.
Responses by status
How many responses came back with each status code, plus Timeout and Failed, with their share.
Per request
One row per request of the target, with its method, count, p50, p95, p99 and error rate. An error rate above 1% is highlighted.

Selecting a window

Once the run has ended, drag across the chart to select a stretch of time, in whole seconds. Everything in the results then covers only that window: the figures, the distribution, the statuses, the per request table, the Requests and Errors tabs and their counts. A Window chip next to the tabs shows the range; click the chart or the chip to clear it and go back to the whole run. The threshold verdict always judges the whole run. The window is not available while the run is in progress, or for a run without per request detail.

Requests

Every request the run made, in a table with the columns # (the position in the run), Time (since the start), VU (the virtual user, from 1), Request (method and URL), Status, Latency (with a bar) and Size of the response. Click a header to sort; the default is slowest first, and latency and size start from the largest value. A line shows how many requests match and the column used to sort them. The bar above the table filters:

  • Search URL or request matches part of the URL or of the request name, ignoring case.
  • A status control: All, one class of status codes (2xx, 4xx, ...) for each class the run had, Timeout and Failed.
  • Latency keeps the requests at or above a value (Any, or ≥ a round number of milliseconds based on the run).
  • VU keeps the requests of one virtual user.
  • Only errors keeps the requests counted as errors.

If nothing matches, the table says No request matches the filters. The table is virtualized, so a long run stays quick to scroll.

Errors

One card for each kind of error in the run or window: an HTTP status (“429 Too Many Requests”), a timeout (“No response in 30 s”) or a failure (“Request failed”). A card shows the number of requests and their share, a small chart of when they happened over the whole run, First · last (the time of the first and the last one), the Affected requests, and an example: the status and the first 160 characters of the body of the first error of that kind (or the error text for a timeout or failure). View requests opens the Requests tab filtered to that status with Only errors on. With no errors the tab says No errors (or No errors in this window).

Comparing runs

The Compare with menu in the header lists the earlier runs of the same target, each with its day and requests per second, and No comparison. Picking a run changes the results in place, there is no separate panel:

  • Each figure of the Summary shows its change against that run. Requests/s, latencies and Total change as a percentage of the previous value. The error rate changes in percentage points: going from 2% to 5% is +3 pt.
  • Higher is better for Requests/s and Total; lower is better for the latencies and Errors. The change is colored accordingly.
  • The chart draws the p99 of that run as a dashed line.
  • The Markdown and PDF exports say which run they were compared with.

Compare runs with the same configuration, or the difference says more about the settings than about your API.

Exporting

The Export menu saves the run to a file you choose (the suggested name is run-0003.md, with the run number and the extension of the format) and shows a notification with the path when it is done. The files cover the whole run, or only the selected window, see below.

FormatContent
Markdown (.md)The summary, the thresholds and the verdict, the figures with their comparison, the per request table, the share of each status and the error groups. GitHub flavored Markdown. The chart and the distribution have no Markdown form and are left out.
PDF (.pdf)An A4 report on white paper, ready to attach: the verdict and thresholds, the figures, the performance chart, the latency distribution with the statuses, the per request table and the error groups. The charts are drawn as vectors.
CSV (.csv)One row per request. The menu shows how many rows it will have.
JSON (.json)The whole run for other tools: the run and its configuration, the summary, the thresholds with the value reached and whether each passed, the series per second (requests per second, virtual users, p50, p90, p95, p99), the histogram, the statuses, the per request statistics, the error groups with an example and every request.

Markdown and PDF follow the interface language, with numbers formatted for it. CSV and JSON are for programs: their column and key names are always English, numbers use a period as the decimal separator, and times and latencies are plain numbers in milliseconds.

The CSV has the columns id, time_ms, vu (from 1), method, request, url, status (the HTTP code, timeout or failed), latency_ms (three decimals), size_bytes and error (1 or 0). The JSON has the top level keys run, summary, thresholds, series, histogram, statuses, per_request, errors and requests. For a run without per request detail the CSV has no rows and the JSON an empty requests list.

While a window is selected, the menu has a checkbox Only the window followed by the range. With it on, every format covers just that window and the file name includes the seconds (run-0003-34-46s.md). With it off, the files cover the whole run.

Copy summary as Markdown, also Ctrl Shift C (Cmd Shift C on macOS) while a load test tab is active, puts the Markdown report on the clipboard instead of in a file. It is handy for a pull request or an issue comment.

Run history

Every run is saved in .postino/runs/ inside the workspace, numbered 0001, 0002 and so on, as two files: 0001.json holds when it started, what it targeted, its configuration (without request bodies or secrets), its thresholds and the final metrics; 0001.samples.csv.gz holds every request the run made, compressed. See Files and folders. Previous runs lists the runs, newest first, with how each one connected (Keep-alive or New connections), and opening one shows its results exactly as when it ended, including the Requests and Errors tabs, the window selection and the exports.

Runs saved by older versions of Postino still open. They have no .samples.csv.gz file, so their Requests and Errors tabs say Runs saved by older versions of Postino have no per request detail, they cannot select a window, and their CSV and JSON exports have no requests. Their figures, charts and histogram are the ones that were saved. Runs saved before the Reuse connections option existed always opened new connections, and show as such.

The Load tests panel of the sidebar lists the runs of the current session with their state and p95.

Whether to commit .postino/runs/ is up to you. Committing it keeps a performance history next to the code; ignoring it keeps the repository small. A run keeps one line per request, so a long run can take a lot of space. See Working with git.

Tips

  • Start small: 5 users for 30 seconds tells you whether the setup works before you push harder.
  • Use a ramp-up. Starting hundreds of users at once measures the connection storm, not steady state.
  • A think time of a few hundred milliseconds makes virtual users behave more like real ones.
  • Keep tests in the post-response script cheap: they run on every iteration.
  • Set thresholds before you start, so a regression shows as Not passed instead of a number you have to remember.
  • Watch the Responses by status panel: a fast run full of 429 or 503 responses is not a fast API.
