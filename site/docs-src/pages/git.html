Working with git

Postino was designed so that requests belong in version control. There is no export step and no sync service: commit the folder, and your team has the same requests, reviewed like any other change.

Recommended layout

Keep the workspace inside the repository of the API it calls:

```text title="shop/" shop/ ├── src/ ├── tests/ ├── api-requests/ # the Postino workspace │ ├── environments/ │ │ ├── local.env │ │ ├── staging.env │ │ └── staging.local.env # ignored │ ├── auth/ │ │ └── login.postino │ └── orders/ │ ├── create.postino │ └── list.postino └── .gitignore ```

Requests then change in the same pull request as the endpoint they call, and checking out an old commit gives you the requests that matched that version of the API.

What to ignore

```text title=".gitignore" # Secrets and personal overrides of Postino environments *.local.env # Load test history, if you do not want to keep it .postino/runs/ ```
  • *.local.env must always be ignored: it is where passwords, tokens and keys go.
  • .postino/runs/ holds the load test run history, a JSON file and a compressed per request log for each run (the second grows with the number of requests). Commit it if you want to keep performance results with the code, ignore it otherwise.
  • A workspace created by Postino, with New workspace or for a Postman import, already has a .gitignore with both lines. Postino never edits the .gitignore of a folder you open, so add them yourself to an existing repository.
  • Postino keeps everything else (settings, recent workspaces, the active environment, logs) outside the workspace, so none of it shows up in your diffs. See Files and folders.

Why the diffs stay clean

  • One request per file. Changing a request touches one file.
  • Line based format. Each header, query parameter and form field is its own line.
  • Canonical output. Postino always writes a request the same way: same section order, same spacing, a single trailing newline, \n line endings on every platform. Saving a request you did not change produces no diff at all.
  • Disable instead of delete. Switching off a header or parameter adds a # at the start of its line, a one character change.
  • Minimal environment edits. Saving an environment rewrites only the lines you changed; comments and order are kept.
```text title="git diff" ::: query genre = science-fiction -limit = 20 +limit = 50 # inStock = true ```

Reviewing request changes

A .postino file reads well on GitHub, GitLab or any diff tool. Reviewers see the exact method, URL, headers, body and tests, with no JSON noise. Use the ::: docs section to explain a request for whoever reads it next.

Merge conflicts

Conflicts in a .postino or .env file are resolved like in any text file. Keep the conflict markers out of the result: a file that still contains <<<<<<< does not parse and shows up as (broken) in the sidebar until you fix it. Postino reads files as they are on disk, so after a pull, reopen the workspace to see the changes.

Source Control

The Source Control button of the activity rail (Alt 2, Ctrl 2 on macOS) lists the files of the workspace that changed since the last commit. Postino runs the git installed on your computer for this: it does not bundle its own git and never stores credentials. If git is missing, the panel says so, with a link to Installing Git and a button to the Git settings (see Settings).

  • Changes groups the files git already tracks, by folder; Unversioned Files the new ones git does not track yet. Requests show their method, like in Collections. The letter at the end is the kind of change: M modified, A added, D deleted, R renamed, U untracked, ! a merge conflict.
  • The checkbox of a file, folder or group chooses what goes into the next commit. It is git's own staging area (the index), so it agrees with git status in a terminal. A box with a dash means only part of the changes is staged.
  • Hovering a row shows Discard changes, which puts the file back as it was in the last commit, or deletes it when it is new. With Confirm before discarding changes on (the default), Postino asks first. Discarded changes cannot be recovered.
  • When the workspace is a folder inside a bigger repository, the panel only lists the workspace's files. If files outside it are staged, a notice warns that they will go into the commit too, with a button to unstage them.
  • When the workspace is not in a repository yet, Initialize repository runs git init in it and adds the .gitignore above when there is none. New workspace does the same with its Initialize a Git repository checkbox, on by default when git is available and hidden when the new folder is already inside a repository.

The list refreshes on its own when files change on disk, when the window gets the focus back and after Postino saves a file, so a commit or a checkout made in a terminal shows up right away.

The status bar

When the workspace is inside a git repository, the status bar shows the current branch, or the short commit hash on a detached HEAD. With git installed Postino asks git; without it, it reads .git/HEAD when the workspace opens and when its window gets the focus back. Worktrees are supported.

Installing Git

Postino needs git 2.30 or later. Check the version you have in a terminal:

```text title="Terminal" git --version ```

Linux

Install it with your distribution's package manager:

```text title="Terminal" sudo apt install git # Debian, Ubuntu, Linux Mint sudo dnf install git # Fedora sudo pacman -S git # Arch, Manjaro sudo zypper install git # openSUSE ```

macOS

Install the Xcode Command Line Tools with xcode-select --install in a terminal, which includes git. With Homebrew, brew install git gives you a more recent version. Until one of them is installed, /usr/bin/git only opens Apple's installer, so Postino reports that the Command Line Tools are missing instead of running it.

Windows

Download Git for Windows and run the installer with its default options, or use winget:

```text title="PowerShell" winget install --id Git.Git -e ```

After installing

Open Settings, Git and click Detect again, or restart Postino. If git is installed somewhere outside your PATH, pick the executable with Browse… in the same section.

Line endings

Postino reads both \n and \r\n and always writes \n. If your repository converts line endings on Windows (core.autocrlf), add this to .gitattributes so files stay identical on every system:

```text title=".gitattributes" *.postino text eol=lf *.env text eol=lf ```
