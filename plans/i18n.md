# Postino internationalization plan

Status: written on 2026-10-01. Source of truth for scope and approach of the UI translation.
Executed phase by phase by Sonnet 5 subagents, orchestrated by the main session, which reviews
each phase, runs the checks and commits. Work happens on the branch `feature/i18n`.

## 0. Rules for whoever executes this plan

- Read `AGENTS.md` first. Its rules apply unchanged: no em dash anywhere (code, comments, docs,
  translations), `make format`, `make lint`, `make test`, max width 100, no `unwrap()`/`expect()`
  outside tests, doc comments on every public item, idle window does no work, nothing in a render
  path costs in proportion to the data size.
- Read the pinned sources before using an API: `rust-i18n-4.2.2`, `rust-i18n-support-4.2.2`,
  `sys-locale-0.3.2`, `gpui-component-0.7.0`, `gpui-base-0.7.0`, `gpui-pre-0.3.7` under
  `~/.cargo/registry/src/*/`.
- Do not commit. The orchestrator reviews the diff and commits each phase.
- Each phase ends with a short report: what was done, deviations and why, the files touched, and
  the summary of `make format`, `make lint` and `make test`.

## 1. Decisions

| Topic | Decision |
|---|---|
| Library | [`rust-i18n`](https://crates.io/crates/rust-i18n) 4.2. It is already compiled into Postino: `gpui-component` uses it for its own strings (`gpui-component-0.7.0/src/lib.rs`, `i18n!("locales", fallback = "en")`). Translations are embedded in the binary at compile time, lookups are a hash map read, and `rust_i18n::set_locale` is process wide, so one call switches both Postino's strings and gpui-component's (calendar, input context menu, ...). |
| Why not Fluent | `fluent`/`fluent-bundle` is the other standard option and handles complex plurals and gender, but it is a second i18n system next to the one gpui-component already ships, adds new crates and needs a runtime loader. The four target languages only need "one"/"other" plurals, which a two-key convention covers (section 3). |
| OS language detection | [`sys-locale`](https://crates.io/crates/sys-locale) 0.3, also already in the dependency tree (through cosmic-text). `sys_locale::get_locales()` returns the user's preferred languages in order (on Linux it reads `LANGUAGE`, `LC_ALL`, `LC_MESSAGES`, `LANG`; on macOS and Windows the system preference list). The first one whose primary language subtag is supported wins; none matching means English. |
| Languages | English (`en`, source and fallback), Spanish (`es`), Galician (`gl`), Italian (`it`). Region variants map to the base language (`es-MX`, `es_ES.UTF-8`, `it-CH`, `gl-ES`). |
| Setting | `language = "auto" | "en" | "es" | "gl" | "it"` in `settings.toml`, default `auto`. Shown in Settings, "Appearance", as the first section ("Language"), a dropdown like the log level one. Options are written in their own language (English, Español, Galego, Italiano), the first one is "Automatic (System)" translated, plus the detected language in parentheses, for example "Automático (Español)". |
| Applying a change | Live, no restart. `rust_i18n::set_locale`, then every view that caches a translated string outside render (input placeholders) re-applies it, then `cx.refresh_windows()`. |
| File format | YAML, `_version: 2` (the same format gpui-component uses): every key lists its four translations together, so adding a key means writing all languages in one place and review is easy. Split by area into several files under `crates/postino-app/locales/` (`common.yml`, `settings.yml`, `request.yml`, `response.yml`, `shell.yml`, `load_test.yml`), so parallel work never edits the same file. |
| Keys | Dotted, area first, lowercase snake case: `settings.appearance.theme_label`, `request.tab.headers`, `common.cancel`. Strings repeated across areas (Cancel, Save, Close, Copy, ...) live under `common.`. |
| What is translated | Every user visible string produced by `postino-app`: labels, buttons, tabs, menus, tooltips, placeholders, empty states, dialog titles and text, inline messages built by the app, command palette actions, status bar, load test dashboard. |
| What is NOT translated | Log messages (they are for bug reports, stay English). Error texts produced by the library crates (`postino-format` parse errors, `postino-http` and `postino-script` errors, test names and messages from user scripts): they are shown verbatim, wrapped in a translated frame where the app adds one ("Could not load the file: {error}"). HTTP vocabulary that is a literal value: method names, header names, status reason phrases, `JSON`, `XML`, MIME types, `.postino` keywords. Keyboard shortcut labels (`Ctrl`, `Cmd`). The `POSTINO_OPEN=components` debug gallery (`views/components/gallery.rs`). Number and date formatting stays as today (decimal point, ISO style); localized number formatting is a possible follow up. |
| Tests and the global locale | The locale is process wide and `cargo test` runs tests in parallel threads, so no test may call `rust_i18n::set_locale`. Tests that need a given language use `t!("key", locale = "es")`. Default locale at startup of a test binary is `en`. |

## 3. Technical design

### 3.1 Dependencies

`[workspace.dependencies]`: `rust-i18n = "4.2"` and `sys-locale = "0.3"`, the exact versions
already in `Cargo.lock` (check that `cargo tree -d --depth 0 | grep -E "i18n|sys-locale"` stays
empty and that no new crate is compiled). `postino-app` depends on both. No other crate does.

### 3.2 Macro and module

- `main.rs`: `rust_i18n::i18n!("locales", fallback = "en");` at the crate root, so `t!` works in
  every module of `postino-app`.
- New `state/locale.rs`, plain Rust with unit tests:
  - `pub enum Language { English, Spanish, Galician, Italian }` with `code()` (`"en"`, ...),
    `native_name()` ("English", "Español", "Galego", "Italiano") and `ALL`.
  - `pub enum LanguageChoice { Auto, Fixed(Language) }` (or a flat enum `Auto, En, Es, Gl, It`,
    whichever reads better with the existing `ThemeChoice` style), with `parse` and serde
    lowercase like the other settings enums.
  - `pub fn match_language(tag: &str) -> Option<Language>`: takes a BCP 47 or POSIX tag
    (`es-ES`, `es_ES.UTF-8`, `gl`, `it_CH@euro`, `C`, `POSIX`) and returns the language of its
    primary subtag, case-insensitive.
  - `pub fn detect(preferred: impl IntoIterator<Item = String>) -> Language`: first match, else
    English. Testable without the OS; the caller passes `sys_locale::get_locales()`.
  - `pub fn resolve(choice: LanguageChoice) -> Language` and `pub fn apply(language: Language)`
    which calls `rust_i18n::set_locale(language.code())`.
- `Settings` gets `language: LanguageChoice` parsed from `settings.toml` like `theme`, unknown
  values fall back to `Auto`.
- `main.rs` applies the language right after loading settings, before opening the window, and
  logs it at Info: `language: es (auto, system locales: es-ES, en-US)`.

### 3.3 Strings in code

- In views: `t!("request.tab.headers")` directly in the element tree. It returns a
  `Cow<'static, str>`; wrap it with `SharedString::from(...)` or `.to_string()` where an API
  needs it. With arguments: `t!("response.size", size = text)` and `%{size}` in the YAML.
- `state/` functions that return `&'static str` labels (`SettingsCategory::label`,
  `InvalidTlsCertificates::label`, `LogLevel::label`, ...) change to return `SharedString` or
  `String` built with `t!` at call time. Never store a translated string in state that outlives a
  render, except where an API forces it (next item).
- Plurals: two keys, `<key>.one` and `<key>.other`, and a small helper in `state/locale.rs`:
  `pub fn plural(key: &str, count: usize) -> String` that picks `one` when `count == 1` and
  passes `count` as an argument. Enough for en, es, gl and it.
- Cached strings: `InputState` placeholders are set once at construction. Each view that owns
  inputs gets a `relocalize(&mut self, window, cx)` method that calls
  `InputState::set_placeholder` again. Lists built once (command palette items, menus) are built
  when they open, so they pick up the current language. On a language change the Settings view
  calls `AppView::relocalize`, which forwards to its children, then `cx.refresh_windows()`.
- Performance: a `t!` lookup per element per render is fine (a hash map read, no allocation for
  plain strings). Do not translate inside loops over rows of a body or a response.

### 3.4 Completeness test

`state/locale.rs` gets a test that reads every key Postino defines (the backend generated by
`i18n!`, `messages_for_locale`, or by parsing the YAML files with the `serde_yaml` already used
by rust-i18n's build if that is simpler) and asserts:

1. every key has a non-empty value for `en`, `es`, `gl` and `it`;
2. every `%{arg}` placeholder in the English text appears in each translation, and no extra ones;
3. no value contains the em dash (U+2014).

And a test that greps the sources: every `t!("literal")` key used under `src/` exists in the
English table (a missing key would otherwise render the key itself at runtime).

## 4. Phases

GitHub issue: one issue "Internationalization: English, Spanish, Galician and Italian" tracks the
whole plan; each phase's commit references it.

### Phase 1. Infrastructure and Settings (one agent)

1. Dependencies (3.1), `i18n!` macro, `state/locale.rs` (3.2) with unit tests for
   `match_language`, `detect` (empty list, `C`, `pt-BR` then `gl-ES` gives Galician, region and
   encoding suffixes) and `plural`.
2. `language` in `Settings`, parse and save, with tests like the existing ones.
3. Startup: resolve and apply before the window opens, log line.
4. Settings, "Appearance": a "Language" section at the top, a dropdown with Automatic (detected
   language) plus the four languages in their native names. Changing it applies live (3.3).
5. Translate everything in `views/settings.rs` and `state/settings.rs` (nav, section titles,
   descriptions, theme cards, fonts, TLS choices, log level labels and descriptions, buttons) into
   `locales/settings.yml` and `locales/common.yml`, all four languages.
6. The `relocalize` plumbing on `AppView`, even if only Settings uses it yet.
7. Completeness tests (3.4).
8. Docs: a short "Translations" section in `AGENTS.md` (library, file layout, key naming, what is
   not translated, tests never call `set_locale`, glossary lives in `plans/i18n.md`).

Acceptance: `make format lint test` clean; with `language = "es"` the whole Settings modal is in
Spanish; switching to Galician in the dropdown updates the open modal at once; `auto` under
`LANG=it_IT.UTF-8` starts in Italian and under `LANG=fr_FR.UTF-8` in English.

### Phase 2. Extract and translate the rest (three agents in parallel)

Each agent owns a disjoint set of source files and its own YAML file, so they never edit the same
file. Common strings: reuse existing `common.*` keys; if one is missing, add it to your own area
file as `<area>.<name>` and list it in the report so the orchestrator can promote it to
`common.yml` afterwards. Do not edit `common.yml`, `settings.yml` or files owned by another agent.

- **Agent A, request side** (`locales/request.yml`): `views/request_editor.rs`,
  `views/define_variable.rs`, `views/snippet_dialog.rs`, `views/env_picker.rs`,
  `views/send.rs`, `views/components/{url_bar,key_value_table,env_pill,inline_message,
  segmented_control,variable_chip,buttons,section_label,card}.rs`,
  `state/{request_edit,define_variable,format,script_heuristics,env_color}.rs`.
- **Agent B, response and shell** (`locales/response.yml`, `locales/shell.yml`):
  `views/response_view.rs`, `views/root.rs`, `views/sidebar.rs`, `views/title_bar.rs`,
  `views/status_bar.rs`, `views/command_palette.rs`, `views/import_menu.rs`,
  `views/components/{document_tabs,underline_tabs,status_badge,method_badge,icon_button}.rs`,
  `state/{response_render,tabs,ui_tabs,palette,sidebar_filter,import,run_log,config,
  debug_open}.rs`, `main.rs` (only user visible strings, not log lines).
- **Agent C, load test** (`locales/load_test.yml`): `views/load_test/*.rs`,
  `state/load_test.rs`.

Each agent: wraps every user visible literal with `t!`, writes en/es/gl/it following the glossary,
adds `relocalize` for its inputs' placeholders and wires it into `AppView::relocalize` (Agent B
owns `root.rs`; A and C expose a method and say in the report where it must be called, B or the
orchestrator wires it), updates unit tests that assert English labels (use
`t!(..., locale = "en")` or compare against the key), and runs `make format lint test`.

Acceptance: no user visible English literal left in the owned files (the agent lists any it left
on purpose and why); completeness tests pass.

### Phase 3. Review and visual check (one agent, then the orchestrator)

1. Promote the duplicated common strings reported in phase 2 into `common.yml`.
2. Language review of all YAML files: consistency with the glossary, natural phrasing, the same
   tone across languages, Galician normative spelling, Italian and Spanish accents.
3. Run the app in Spanish and Italian (the longest languages) at the default 1280x760 window and
   at 1000 px wide, drive it with xdotool (see the project memory on xdotool for the recipe) and
   take screenshots of: main screen with a response, every request tab, the sidebar context
   menu, command palette, import menu, environment picker, Define variable dialog, Code snippet
   dialog, Settings (every category), load test tab (config and dashboard). Fix clipped or
   overflowing labels (truncate with ellipsis or allow wrapping, never shrink fonts).
4. Idle check from `AGENTS.md`: with the app idle for 10 s after a language switch, CPU ticks
   barely move and GPU counters do not move.

Acceptance: screenshots reviewed by the orchestrator, no clipped text, all checks clean. Then
the user checkpoint and merge of `feature/i18n` into `main`.
